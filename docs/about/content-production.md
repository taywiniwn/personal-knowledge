# 内容如何生产

想法捕获与知识沉淀是两件独立的事。把它们混在一起成本太高——要想清楚放哪里、怎么表达、和现有内容的关系，这些判断成本会让大量想法停留在「该写但还没写」。

本站把两件事分开处理。

## 1. 捕获：极低摩擦

[GitHub Issues](https://github.com/taywiniwn/personal-knowledge/issues) 是随时可以扔东西进去的收件箱：标题、几行文字、截图、链接都行。不需要想结构、措辞或归属。

建议标签：

| 标签 | 用途 |
| --- | --- |
| `inbox` | 尚未处理 |
| `pillar:health` / `pillar:career` / `pillar:finance` / `pillar:life` | 粗分归属 |
| `data` | 客观数据相关 |
| `done` | 已融入文档并关闭 |

## 2. 整合：由 LLM 完成

判断归属、提炼观点、找到现有文档接入点、写成连贯表达——这些认知成本交给 LLM。LLM 应同时看到全部待处理 Issue 与全部现有 Markdown。

目标是**真正的融合**，不是简单追加。关键约束：

- 优先改已有页面，而不是新建页面
- 页面数量几乎不变，知识密度在增长
- 结构由人定，内容由 LLM 填充，主权在人

这与「让 LLM 每次独立写 Wiki」不同：后者不知道已有什么、该放哪里。这里的 LLM 角色是**编辑**。

## 3. 两类输入源

### 思维与认知

书摘、稍后阅读、灵感、对话触发的认知……共同点是捕获窗口极短。流程：捕获为 Issue → LLM 判断增量价值 → 融入现有文档 → 关闭 Issue。

### 客观数据

投资持仓、健康导出等有固定结构，适合脚本同步到 `static/data/`，由页面读取 JSON 渲染图表（见 [财务看板](/charts/finance)）。

## 推荐工作流

```text
捕获（Issue） → LLM 审阅全库 → 融入已有 Markdown → PR 审阅 → 构建发布
                 ↑                              ↓
            可选：脚本写入 static/data/*.json → 图表页展示
```
